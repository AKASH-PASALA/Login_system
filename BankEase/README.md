# BankEase -- Secure User Registration and Login System

BankEase is a C++ desktop application demonstrating user registration
and authentication. It combines object-oriented programming, input
validation, Argon2id password hashing, CSV file storage, and a native
Windows GUI built with the Win32 API.

> **Project scope:** BankEase is an authentication-system project, not a
> real banking application. It does not process deposits, withdrawals,
> payments, or financial transactions.

## 1. Project objectives

-   Register new users.
-   Validate user details before saving.
-   Hash passwords before storage.
-   Store user records in a CSV file.
-   Authenticate users with username and password.
-   Provide graphical registration and login screens.
-   Demonstrate C++ OOP, file handling, security, and Windows GUI
    programming.

## 5. Source files and responsibilities

### `src/models/User.h` and `User.cpp`

Define the base `User` class. It stores common user information: - User
ID - Full name - Phone number - Email address

The class provides constructors, getters, setters, and profile-display
functionality.

### `src/models/Customer.h` and `Customer.cpp`

Define `Customer`, which derives from `User`. Customer-specific
information includes the username and registration status.

### `src/utils/Validator.h` and `Validator.cpp`

Contain reusable validation functions:

  Function                 Purpose
  ------------------------ -----------------------------------------------
  `isValidName()`          Checks name format
  `isValidEmail()`         Checks email format
  `isValidPhoneNumber()`   Checks for a 10-digit phone number
  `isValidUsername()`      Checks username length and allowed characters
  `isValidPassword()`      Checks password strength
  `isPasswordMatching()`   Checks password confirmation

The current username rule accepts 4--20 letters, digits, or underscores.
A username containing spaces, such as `Chethan ram`, is rejected;
`Chethan_ram` is an example of an acceptable format.

The password rule requires at least eight characters, including
uppercase and lowercase letters, a digit, and a special character.

### `src/security/PasswordManager.h` and `PasswordManager.cpp`

Responsible for password hashing and verification.

-   `generateSalt()` -- generates a random salt.
-   `hashPassword()` -- creates an Argon2id encoded password hash.
-   `verifyPassword()` -- verifies an entered password against the
    stored encoded hash.

The current Argon2id configuration is:

  Parameter                                Value
  ------------------------ ---------------------
  Algorithm                             Argon2id
  Iterations / time cost                       3
  Memory cost                65,536 KiB (64 MiB)
  Parallelism                                  1
  Hash length                           32 bytes
  Salt length                           16 bytes

The encoded Argon2id string contains its parameters, salt, and derived
hash, so a separate CSV salt column is not required.

**Security note:** The current implementation uses C++
`std::random_device` for salt generation. Its cryptographic strength
depends on the implementation. A production system should use a
cryptographically secure operating-system random-number generator and
undergo a broader security review.

### `src/database/Database.h` and `Database.cpp`

Manage persistent records in `data/users.csv`.

Responsibilities: - Initialize the CSV database. - Check whether a
username already exists. - Check whether an email already exists. - Save
a customer and encoded password hash. - Find a user by username. -
Generate the next user ID. - Parse quoted CSV fields correctly.

The CSV header is:

``` csv
userId,fullName,phoneNumber,email,username,passwordHash,isRegistered
```

The password column stores the Argon2id encoded hash, not the plaintext
password. CSV quoting is important because an Argon2id encoded string
contains commas in its parameter section.

### `src/authentication/Authentication.h` and `Authentication.cpp`

Coordinate validation, password security, and database operations.

-   `signup()` -- validates details, checks for duplicate
    username/email, hashes the password, creates a customer record, and
    saves it.
-   `login()` -- looks up the username, verifies the password hash,
    checks registration status, and establishes the session.
-   `logout()` -- ends the current session.
-   `isLoggedIn()` -- reports session state.
-   `getCurrentUser()` -- provides the authenticated customer.

### `src/main.cpp`

Contains the console application's entry point and text-based menu. The
console flow includes signup, login, dashboard/profile viewing, and
logout.

### `src/gui/gui_main.cpp`

Contains the Windows GUI entry point and Win32 window logic.

It uses: - `WinMain()` as the GUI entry point. - `WNDCLASS` and
`RegisterClass` to register the window class. - `CreateWindowA()` to
create the main window and controls. - Static controls for labels, edit
controls for input, and buttons for actions. - `WindowProcedure()` to
handle Windows messages and button events. - `ShowWelcomeScreen()`,
`ShowLoginScreen()`, and `ShowSignupScreen()` to switch screens. -
`HandleLogin()` and `HandleSignup()` to pass form data to the existing
authentication module. - `ES_PASSWORD` to mask password characters in
GUI input fields.

The GUI reuses the backend classes; it does not need a separate database
or password-hashing implementation.

## 7. Data flow: user registration

When a person signs up, information moves from the GUI or console
through the authentication layer and into the CSV database.

### Registration data-flow steps

1.  The user enters full name, phone number, email, username, password,
    and confirm password.
2.  The UI passes these values to `Authentication::signup()`.
3.  The authentication module asks `Validator` to check the fields.
4.  The authentication module checks the database for an existing
    username and email.
5.  `PasswordManager` generates a salt and creates an Argon2id encoded
    hash from the password.
6.  The application generates the next user ID and creates a `Customer`
    object.
7.  `Database::saveUser()` writes the customer information and encoded
    password hash to `data/users.csv`.
8.  The application reports registration success or failure to the UI.

``` text

                |
                v
    Authentication::signup()
                |
                v

                |

          /          \
        No            Yes
        |              |
        v              v
 Return error     Check duplicate
                  username/email
                       |
                No duplicates?
                  /       \
                No         Yes
                |           |
                v           v
           Return error  Generate salt
                             |
                             v
                       Argon2id hash
                             |
                             v
                       Create Customer
                             |
                             v
                     Database::saveUser()
                             |
                             v
                       users.csv updated
                             |
                             v

```

### What information is stored?

The CSV file has these columns:

  Column           Stored value
  ---------------- --------------------------------
  `userId`         Generated user ID
  `fullName`       User's full name
  `phoneNumber`    User's phone number
  `email`          User's email address
  `username`       Chosen username
  `passwordHash`   Argon2id encoded password hash
  `isRegistered`   Registration status

**The plaintext password is not supposed to be stored in the CSV file.**
The application stores the encoded Argon2id hash instead. The encoded
hash includes the salt and parameters required for later verification.

## 8. Data flow: user login and authentication

Login is an authentication process: the application checks whether the
password supplied by the user matches the password hash saved during
registration.

### Login data-flow steps

1.  The user enters a username and password.
2.  The UI passes them to `Authentication::login()`.
3.  The authentication module asks the database to find the record for
    that username.
4.  If no matching username is found, login is rejected.
5.  If a record is found, the database returns the customer details and
    stored Argon2id encoded hash.
6.  `PasswordManager::verifyPassword()` passes the entered password and
    stored encoded hash to Argon2id verification.
7.  Argon2id uses the salt and parameters encoded in the stored hash to
    verify the candidate password.
8.  If verification succeeds and the account is registered,
    authentication succeeds and the current-user/session state is set.
9.  If the username is not found, the password is incorrect, or the
    account is not registered, authentication fails.
10. The UI displays the result.

``` text
User enters username + password
                |
                v
        Login form / console
                |
                v
      Authentication::login()
                |
                v
 Database::findUserByUsername()
                |
        User record found?
          /          \
        No            Yes
        |              |
        v              v
   Reject login   Retrieve stored
                  encoded hash
                       |
                       v
          PasswordManager::verifyPassword()
                       |
                Password matches?
                  /       \
                No         Yes
                |           |
                v           v
           Reject login  Check registered
                         account status
                              |
                       Account registered?
                         /        \
                       No          Yes
                       |            |
                       v            v
                  Reject login  Set session /
                                current user
                                     |

```

### How password verification works

BankEase does not decrypt the password stored in the CSV file.

During registration: - A random salt is generated. - Argon2id receives
the password, salt, and configured cost parameters. - Argon2id produces
an encoded hash. - The encoded hash is saved in the CSV file.

During login: - The entered password is supplied to the Argon2id
verification function along with the stored encoded hash. - The encoded
hash contains the salt and parameters needed for verification. -
Argon2id checks whether the entered password corresponds to that hash. -
The verification result is true or false.

This is password hashing and verification, not password encryption and
decryption.

## 9. How data is stored and retrieved

BankEase uses a CSV file as a simple persistent data store.

### Storage location

``` text
BankEase/
└── data/
    └── users.csv
```

The database module uses the relative path `data/users.csv`. Therefore,
run the executable from the `BankEase` project root so the application
resolves the file path correctly.

### Saving a user

The registration flow eventually calls `Database::saveUser()`. That
function serializes the customer details and encoded password hash as a
CSV record and appends it to the file. Fields are quoted or escaped when
necessary.

### Retrieving a user

The login flow calls `Database::findUserByUsername()`. The database
module reads the CSV records, parses the fields, locates the matching
username, and returns the customer details and stored password hash to
the authentication layer.

### Checking duplicate records

Before saving a new user: - `usernameExists()` checks whether the
username is already present. - `emailExists()` checks whether the email
is already present.

This prevents the registration flow from creating another record with an
already-used username or email, based on the records currently in the
CSV file.

### Why CSV?

CSV was chosen because it is simple, human-readable, easy to inspect
during development, and does not require setting up a database server.
It is suitable for demonstrating file handling in a small academic
project.

CSV is not a full database-management system. It does not automatically
provide transactions, multi-user concurrency control, access
permissions, or robust recovery. A larger application should use a
database system and apply appropriate security controls to the stored
records.

## 10. Algorithms used

### A. Registration algorithm

1.  Read the full name, phone number, email, username, password, and
    confirmation.
2.  Check that required fields are not empty.
3.  Validate each field using the `Validator` functions.
4.  Check whether the username already exists.
5.  Check whether the email already exists.
6.  Generate a random salt.
7.  Use Argon2id to derive an encoded password hash.
8.  Generate the next user ID.
9.  Create a `Customer` object.
10. Save the customer details and encoded hash to `users.csv`.
11. Report whether registration succeeded.

### B. Login algorithm

1.  Read the username and password.
2.  Find the stored user record using the username.
3.  Retrieve the stored Argon2id encoded hash.
4.  Verify the entered password using `argon2id_verify`.
5.  Check that the account is registered.
6.  If verification succeeds, establish the logged-in session.
7.  Otherwise, reject the login.

### C. Argon2id password hashing

Argon2id is a memory-hard password-hashing algorithm.

1.  Generate a unique random salt for the password.
2.  Pass the password, salt, and configured cost parameters to Argon2id.
3.  Argon2id performs its memory- and time-intensive computation.
4.  Store the resulting encoded hash.
5.  During login, use the encoded hash to verify the entered password.

A unique salt means identical passwords do not normally produce
identical encoded hashes.

### D. CSV parsing

The database module reads and writes structured CSV records. Fields
containing commas or other special CSV characters must be quoted and
escaped correctly. The parser handles quoted fields so commas inside an
Argon2id hash are not mistaken for column separators.

### E. Input validation

Validation functions apply format rules before a new record is stored.
This keeps validation reusable instead of duplicating it in the console
and GUI.

### F. GUI event handling

1.  Windows sends a message when a user clicks a button or interacts
    with a control.
2.  `WindowProcedure()` receives and handles the message.
3.  The selected action switches screens or calls the authentication
    module.
4.  The result is displayed through a message box.

## 11. OOP concepts used

  -----------------------------------------------------------------------
  OOP concept                         How it is used
  ----------------------------------- -----------------------------------
  **Class**                           `User`, `Customer`, `Validator`,
                                      `PasswordManager`, `Database`, and
                                      `Authentication` organize data and
                                      operations.

  **Object**                          `Customer` objects represent user
                                      records; the GUI creates an
                                      `Authentication` object to use the
                                      backend.

  **Encapsulation**                   User data is held inside the model
                                      class and accessed through public
                                      methods such as getters and
                                      setters.

  **Inheritance**                     `Customer` inherits common user
                                      information and behavior from
                                      `User`.

  **Abstraction**                     Operations such as `signup()`,
                                      `login()`, `saveUser()`, and
                                      `verifyPassword()` hide their
                                      internal steps behind method
                                      interfaces.

  **Composition / has-a               `Authentication` uses a `Database`
  relationship**                      object to perform storage
                                      operations.

  **Modularity**                      Separate classes and source files
                                      divide validation, security,
                                      persistence, models,
                                      authentication, and GUI
                                      responsibilities.
  -----------------------------------------------------------------------

### Is polymorphism used?

The current implementation does not demonstrate clear runtime
polymorphism through virtual functions and overridden methods. Do not
claim runtime polymorphism is implemented unless virtual methods and
overriding are added.

## 16. Conclusion

BankEase demonstrates how a C++ application can combine object-oriented

authentication responsibilities, making the project easier to
understand, test, and extend.
